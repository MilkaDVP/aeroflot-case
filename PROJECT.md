> Этот файл — единый контекст проекта. Claude Code читает его в каждой сессии.
> Не пересказывай контекст в чате — добавляй сверху только свою текущую задачу.

## 1. КОНТЕКСТ И ЗАДАЧА

Конкурсное задание ПАО «Аэрофлот», технологическое направление, транспортная
сфера «Авиаперевозки». Команда из 3 человек.

**Проблема.** При обнаружении дефекта на воздушном судне (ВС) экипаж вызывает
инженера. По регламенту Аэрофлота сотрудник обязан прибыть к ВС не позднее чем
через 15 минут. Сейчас диспетчер назначает инженера вручную, не зная его
реального местоположения и текущей загрузки, сверяясь с бумажными данными. Это
приводит к неоптимальным назначениям, увеличивает простой ВС, повышает риск
задержек рейсов и создаёт имиджевые потери для авиакомпании.

**Решение.** Система из трёх компонентов, которая при поступлении вызова
автоматически находит ближайшего свободного сотрудника с действующим допуском
на данный тип ВС и данный вид работ, укладывающегося в регламент 15 минут,
визуализирует маршрут и уведомляет инженера на его устройстве.

## 2. АРХИТЕКТУРА

```
┌──────────────────┐         ┌────────────────┐         ┌──────────────────┐
│  Веб-диспетчер   │ ←────→  │     Сервер     │ ←────→  │  PWA инженера    │
│    (браузер)     │  REST   │ FastAPI+SQLite │  REST   │   (телефон)      │
└──────────────────┘         └────────────────┘         └──────────────────┘
```

### Компоненты

**`server/`** — единая точка правды
- FastAPI + SQLite (без внешней СУБД, поднимается «из коробки»)
- Аутентификация, роли, привязка пользователя к аэропорту
- Хранит сотрудников, их квалификации, координаты, статусы, вызовы, историю
- Содержит алгоритм подбора (не на клиенте — чтобы логика была одна)
- REST API, автодокументация Swagger на `/docs`

**`web-dispatcher/`** — рабочее место диспетчера
- Чистый HTML/JS/CSS без фреймворков
- Экран входа → выбор аэропорта/смены → рабочий экран
- SVG-карта аэропорта, панель сотрудников, форма вызова, визуализация маршрута
- Polling данных с сервера раз в 3–5 секунд

**`mobile-engineer/`** — PWA для инженера
- Тот же стек HTML/JS, устанавливается на телефон, работает как приложение
- Вход по учётной записи инженера
- GPS через Geolocation API + режим имитации (ручной ввод координат для демо)
- Приём вызова, карта с маршрутом до ВС, смена статуса

**`data/`** — офлайн-подготовка карт
- Python-скрипт выгрузки аэропортов из OpenStreetMap через Overpass API
- Запускается один раз, результат коммитится в репозиторий как JSON

## 3. КВАЛИФИКАЦИИ (по ФАП-147 / ФАП-285)

Это не выдуманная классификация — она соответствует реальной системе
свидетельств авиационного персонала РФ. Использовать строго её.

### Квалификационные отметки в свидетельстве специалиста по ТО

| Отметка | Область работ | Отношение к ОТО на перроне |
|---|---|---|
| **A** | Оперативное ТО, устранение простых дефектов в пределах ограничений на специфические виды работ | Основная рабочая категория для перрона |
| **B1** | Планер, двигатели, механические и электрические системы | Сложные механические дефекты |
| **B2** | Авионика, электрические и радиоэлектронные системы | Дефекты авионики и электроники |
| **C** | Базовое (периодическое) ТО, право подписи свидетельства о ТО | Начальник смены, подтверждающий персонал |

### Подкатегории по типу ВС

Отметки A и B1 дробятся по типу воздушного судна:

| Подкатегория | Тип ВС |
|---|---|
| A1 / B1.1 | Самолёты с газотурбинными двигателями |
| A2 / B1.2 | Самолёты с поршневыми двигателями |
| A3 / B1.3 | Вертолёты с газотурбинными двигателями |
| A4 / B1.4 | Вертолёты с поршневыми двигателями |

B2 и C по типу двигателя не дробятся.

### Допуск на конкретный тип ВС (type rating)

Помимо категории, в свидетельство вносится **конкретный тип ВС**, на котором
разрешено выполнять ТО: A320, A330, B737, B777, SSJ-100, MC-21 и т. д.

**Это второе обязательное измерение подбора.** Инженер с отметкой B1.1 на A320
не имеет права обслуживать B777, даже если он ближе всех и свободен. Система
обязана это учитывать — иначе она предложит юридически недопустимое назначение.

### Модель квалификации сотрудника

```
qualifications: [
  { category: "B1.1", aircraft_types: ["A320", "A321"], valid_until: "2027-03-15" },
  { category: "A1",   aircraft_types: ["A320", "B737"], valid_until: "2027-08-01" }
]
```

Проверяется: категория подходит под вид работ + тип ВС в списке допусков +
срок действия отметки не истёк.

## 4. СПРАВОЧНИК НЕИСПРАВНОСТЕЙ

Соответствие «тип дефекта → требуемая категория». Дефекты сгруппированы по
главам ATA-100 — это отраслевой стандарт, применяемый в эксплуатационной
документации.

| Код | Дефект | ATA | Требуемая категория |
|---|---|---|---|
| `engine_start_fault` | Отказ запуска двигателя | 71–80 | B1 |
| `hydraulic_leak` | Утечка гидрожидкости | 29 | B1 |
| `landing_gear_fault` | Неисправность шасси | 32 | B1 |
| `fuselage_damage` | Повреждение обшивки/планера | 53 | B1 |
| `brake_wear` | Износ тормозов, замена колеса | 32 | A |
| `fuel_system_fault` | Неисправность топливной системы | 28 | B1 |
| `nav_system_error` | Ошибка навигационной системы | 34 | B2 |
| `comm_radio_fault` | Отказ радиосвязи | 23 | B2 |
| `display_failure` | Отказ индикации в кабине | 31 | B2 |
| `autopilot_fault` | Отказ автопилота | 22 | B2 |
| `cabin_light_fault` | Отказ освещения салона | 33 | A |
| `apu_fault` | Неисправность ВСУ | 49 | B1 |

Категории **A** достаточно для простых дефектов; для сложных требуется **B1**
или **B2**. Сотрудник с B1 может закрыть и работы уровня A по своей области —
это учитывается в алгоритме как иерархия допусков.

## 5. АВТОРИЗАЦИЯ И РОЛИ

Система не открывается сразу на карте. Вход обязателен.

### Роли

| Роль | Доступ |
|---|---|
| `dispatcher` | Рабочий экран диспетчера своего аэропорта: приём вызовов, подбор, назначение |
| `shift_supervisor` | То же + переопределение решения системы с обязательным указанием причины |
| `engineer` | Только PWA: свои вызовы, свой статус, свой маршрут |
| `admin` | Управление сотрудниками, квалификациями, аэропортами, справочниками |

### Сценарий входа диспетчера

```
1. Экран входа          → логин / пароль
2. Выбор аэропорта      → только те, к которым пользователь привязан
                          (если привязан к одному — шаг пропускается)
3. Выбор смены          → дневная / ночная, отображается состав смены
4. Рабочий экран        → карта выбранного аэропорта
```

### Сценарий входа инженера (PWA)

```
1. Экран входа          → логин / пароль
2. Подтверждение выхода на смену
                        → статус меняется на "free",
                          запускается передача GPS-координат
3. Рабочий экран        → «вызовов нет» либо активный вызов с маршрутом
```

### Важно

- Аэропорт — это **контекст сессии**. Диспетчер видит только сотрудников, ВС и
  вызовы своего аэропорта. Данные разных аэропортов не смешиваются
- Смена определяет, кто вообще является кандидатом на назначение: сотрудник не
  на смене не рассматривается независимо от координат
- Для демонстрации жюри в БД предзагружены готовые учётные записи всех ролей,
  они указаны в README

## 7. АЛГОРИТМ НАЗНАЧЕНИЯ

Порядок шагов строго такой:

1. Диспетчер фиксирует вызов: борт, стоянка, код дефекта
2. По справочнику определяется требуемая категория (A / B1 / B2)
3. Из типа ВС берётся требуемая подкатегория (например, A320 → B1.1)
4. **Фильтр допуска:** у сотрудника есть отметка нужной категории (или выше по
   иерархии), тип ВС входит в его допуски, срок действия отметки не истёк
5. **Фильтр доступности:** сотрудник на текущей смене и в статусе `free`
6. Для каждого кандидата — кратчайший путь до стоянки по графу (Дейкстра)
7. Время в пути = расстояние / скорость (пешком ≈ 5 км/ч, спецтранспорт ≈ 20 км/ч,
   для спецтранспорта учитываются только рёбра с `vehicle_allowed`)
8. Отсев кандидатов со временем > 15 минут
9. Выбор минимального по времени

**Инвариант, проверяемый тестами:** среди кандидатов, прошедших фильтры допуска
и доступности, система никогда не назначает сотрудника, который будет в пути
дольше другого доступного кандидата.

**Внештатная ситуация.** Если ни один кандидат не проходит по 15 минутам либо
нет никого с нужным допуском — система не молчит, а выдаёт диспетчеру:
- ближайшего по времени кандидата с пометкой о превышении регламента
- список сотрудников с нужным допуском, занятых на других вызовах, и время их
  освобождения
- явное предупреждение о нарушении регламента, требующее решения человека

**Граф маршрутов.** Вершины — стоянки ВС, техцентр, узлы рулёжек. Рёбра —
участки taxiway с весом = расстояние в метрах и флагом проезда спецтранспорта.
Координаты lat/lon конвертируются в 2D линейной проекцией.

**Ограничение по времени:** расчёт и выдача предложения — не более 10 секунд.

## 8. API (контракт между компонентами)

Зафиксирован заранее, менять только по согласованию всей команды.

```
АУТЕНТИФИКАЦИЯ
POST   /api/auth/login                вход, возвращает токен и роль
POST   /api/auth/logout               выход
GET    /api/auth/me                   текущий пользователь, роли, аэропорты

АЭРОПОРТЫ
GET    /api/airports                  аэропорты, доступные пользователю
GET    /api/airports/{icao}           граф аэропорта (nodes + edges)
POST   /api/session/airport           выбрать аэропорт как контекст сессии

СОТРУДНИКИ
GET    /api/employees                 сотрудники текущего аэропорта и смены
POST   /api/employees                 создать (только admin); сразу на смене
                                      (on_shift) и логин/пароль для PWA — по желанию
PATCH  /api/employees/{id}            обновить статус/квалификации
POST   /api/employees/{id}/location   обновить координаты (шлёт PWA)
POST   /api/employees/{id}/shift      выход на смену / уход со смены

ВОЗДУШНЫЕ СУДА
GET    /api/aircraft                  ВС на стоянках текущего аэропорта
POST   /api/aircraft                  поставить борт на стоянку (только admin)
DELETE /api/aircraft/{id}             убрать борт (нельзя при открытом вызове)

СПЕЦТРАНСПОРТ (этап 2)
GET    /api/vehicles                  машины парка: где стоят и у кого
POST   /api/vehicles                  поставить машину в парк (только admin)
DELETE /api/vehicles/{id}             вывести из парка (только свободную)

АДМИНИСТРИРОВАНИЕ АЭРОПОРТОВ (только admin)
GET    /api/admin/airports            все аэропорты с размером графа
POST   /api/admin/airports/import     выгрузить граф из OSM по коду ИКАО
POST   /api/admin/airports            создать пустой аэропорт для разметки
PUT    /api/admin/airports/{icao}/graph  сохранить размеченный граф (с проверками)
DELETE /api/admin/airports/{icao}     удалить (только созданный и пустой)

ВЫЗОВЫ
GET    /api/calls                     активные вызовы аэропорта
POST   /api/calls                     создать вызов (борт, стоянка, код дефекта)
POST   /api/calls/{id}/suggest        подбор → кандидат, маршрут, ETA, альтернативы
POST   /api/calls/{id}/assign         назначить (при переопределении — с причиной;
                                      занятому — в очередь, только начальник смены)
POST   /api/calls/{id}/unassign       снять исполнителя (причина обязательна):
                                      вызов возвращается к подбору
PATCH  /api/calls/{id}/status         смена статуса

ДЛЯ PWA ИНЖЕНЕРА
GET    /api/me/current-call           текущий вызов инженера с маршрутом
                                      и числом вызовов в очереди (queued_count),
                                      машиной и где её забрать (vehicle)
POST   /api/me/status                 принял / прибыл / завершил

СПРАВОЧНИКИ
GET    /api/defect-types              коды дефектов с требуемыми категориями
GET    /api/aircraft-types            типы ВС и подкатегория допуска
```

Обмен — REST + polling раз в 3–5 секунд. WebSocket не используем: для
демонстрации polling проще и надёжнее.

## 9. ДИЗАЙН-НАПРАВЛЕНИЕ

Это рабочий инструмент диспетчера на всю смену, а не лендинг. Ориентир:
авиационные диспетчерские системы, ATC-интерфейсы, промышленные SCADA-панели.

**Принципы:**
- Тёмная тема как основная — диспетчерская работает круглосуточно
- Карта занимает большую часть экрана, панели по бокам её не перекрывают
- Плотная информационная сетка, без воздушных лендинг-отступов
- Цвет несёт смысл, а не украшает:
  - зелёный — свободен и имеет допуск
  - серый — свободен, но нет допуска на этот тип ВС
  - жёлтый — близко к лимиту 15 минут
  - красный — превышение регламента
  - синий — предложенный маршрут
- Моноширинный шрифт для цифр (время, координаты, номера бортов)
- Крупные значения времени в пути — главная цифра для диспетчера
- Квалификация показывается как отметка из свидетельства (`B1.1 / A320`), а не
  описательным текстом — так, как её видит настоящий диспетчер
- Анимации только функциональные: подсветка нового вызова, отрисовка маршрута

**С первого взгляда, без чтения текста, должно считываться:** кто свободен, у
кого есть допуск на этот борт, кто предложен системой, уложится ли он в 15 минут.

**Экран входа и выбора аэропорта** — тот же визуальный язык, минимум элементов,
без «маркетингового» оформления.

**PWA инженера** — та же палитра, но интерфейс под одну руку и крупные кнопки:
человек смотрит в телефон на ходу, в перчатках, при ярком солнце. Главный
экран — куда идти и сколько осталось.

## 10. ТРЕБОВАНИЯ ЗАДАНИЯ

Обязательны к выполнению, по ним начисляются баллы.

**Функциональные:**
- Учёт регламента ПАО «Аэрофлот» — 15 минут на прибытие
- Классификация сотрудников по квалификации и специализации
- Автоматический расчёт времени прибытия, времени убытия, оптимального маршрута
- Учёт наличия поблизости спецтранспорта и его влияния на маршрут
- Визуализация сотрудников, ВС, спецтранспорта и маршрута на интерактивной карте
- Уведомление сотрудника через программный интерфейс (приложение/бот)

**Контрольные тесты:**
- Минимум 5 сценариев: разное расположение сотрудников, разная специализация,
  несколько вызовов подряд, внештатные условия
- Время расчёта и выдачи предложения — не более 10 секунд
- Сравнение с «интуитивным» выбором диспетчера

### Этап 1, шаг 1 — данные и граф ✅

**`data/fetch_airport.py`** — выгрузка аэропорта из OSM через Overpass API.
Только стандартная библиотека, зависимостей нет. Каталог аэропортов внутри
скрипта: UUEE, UUDD, ULLI. Флаги: `--list`, `--no-patch`, `--service-roads`,
`--raw <файл>` (сборка из сохранённого ответа, без сети).

Как строится граф: линии OSM режутся по точкам, которые принадлежат двум и
более линиям, являются концами линий или помечены как стоянки. Каждый отрезок
между вершинами — ребро, длина считается по всем промежуточным точкам.
ВПП (`runway`) в граф не входят: маршрут сотрудника не может идти через полосу.
Остаётся только наибольшая связная компонента — обрывки на краю рамки
отбрасываются, иначе Дейкстра на них молча вернёт «пути нет».

**`data/patches/UUEE.patch.json`** — ручные правки поверх выгрузки, отдельным
файлом, чтобы на защите было видно границу между данными OSM и нашей моделью.
Сейчас там три техцентра (`tc_west`, `tc_north`, `tc_east`), посаженные на
координаты реальных ангаров из OSM; `connect_nearest` привязывает их к
ближайшим узлам рулёжной сети.

**`data/airports/UUEE.json`** — готовый граф Шереметьево, закоммичен:
1803 узла, 2605 рёбер, **179 стоянок с реальными номерами**, 3 техцентра,
охват 7.3 × 2.9 км. Сырой ответ Overpass в git не идёт (`.gitignore`).

### Этап 1, шаг 3 — допуски и подбор ✅

**`server/constants.py`** пополнен квалификационной моделью: семейства
отметок, четыре группы ВС, таблица `AIRCRAFT_GROUP_BY_TYPE` (17 типов),

**Иерархия допусков `CATEGORY_SUBSTITUTIONS`** — три решения, принятые явно
и закомментированные в коде, потому что их могут спросить на защите:
1. B1 закрывает работы уровня A по своей области (прямо следует из ТЗ);
2. **B2 не закрывает A** — консервативно: система не должна предлагать
   назначение, законность которого придётся доказывать;
3. **C не подменяет линейные категории** — это право подписи, а не право
   выполнять оперативное ТО на перроне.

**`server/algorithm/qualification.py`** — разбор отметок (`A1`, `B1.3`, `B2`,
`C`), расчёт требуемой отметки из пары «дефект + тип ВС», проверка иерархии,
типа ВС и срока действия. Отказ возвращается с конкретной причиной
(«отметка B1.1 есть, но без допуска на A320»), а не как «не подходит»:
диспетчер должен иметь возможность оспорить решение системы.

**`server/algorithm/dispatch.py`** — функция `suggest()`. Порядок фильтров:
смена → допуск → доступность → маршрут → сортировка по времени. Допуск
проверяется раньше занятости намеренно: занятость временна, отсутствие
допуска непреодолимо. Отсева по 15 минутам внутри нет — превысившие
регламент остаются в списке с флагом `within_regulation=False`, иначе во
внештатной ситуации диспетчер остался бы вообще без вариантов. Занятые
с допуском выдаются отдельным списком с временем освобождения.
Модуль не знает про БД и работает с обычными словарями.

### Этап 1, шаг 4 — сервер, авторизация, API ✅

**Стек:** FastAPI + SQLAlchemy 2.0 + Pydantic v2 + SQLite. Внешних СУБД нет.

**`server/database.py`** — движок и сессия. **`server/models/`** — `User`,
`AuthSession`, `Airport`, `Employee`, `Aircraft`, `Call` по модели данных §6.
Граф аэропорта в БД не хранится: он неизменен и живёт в памяти
(`server/graph_registry.py`), иначе каждый подбор начинался бы с разбора
JSON на 700 КБ. Квалификации — JSON-поле, а не таблица: алгоритм работает
с ними как со списком словарей, отдельная таблица дала бы три JOIN
на каждый подбор без выигрыша.

**`server/auth/`** — вход по токену в таблице `auth_sessions`. Пароли —
PBKDF2-HMAC-SHA256, 200 000 итераций, стандартная библиотека, без `passlib`.
Сравнение через `compare_digest`. Контекст сессии (аэропорт + смена) хранится
на сервере: подменить аэропорт параметром запроса нельзя.

**`server/api/`** — весь контракт §8 плюс `/api/health` и `/api/aircraft-types`.
Swagger на `/docs`.

Решения, заметные в коде:
- стоянка и требуемая отметка вычисляются на сервере из карточки борта
  и справочника, а не приходят от клиента — иначе появился бы способ
  обойти проверку допуска подстановкой значения;
- переопределение решения системы доступно только `shift_supervisor`
  и `admin`, причина обязательна, в вызове сохраняются **оба** решения —
  и предложение системы, и выбор человека;
- `check_same_airport` вынесена в зависимость и вызывается при каждом
  доступе к объекту — иначе однажды её где-нибудь забудут.

**`server/seed.py`** — 12 сотрудников, 6 бортов, 6 учётных записей,
2 открытых вызова. Расстановка рассчитана так, чтобы все семь ситуаций
(разное расположение, чужой допуск, истёкшая отметка, спецтранспорт,
все заняты, нет допуска ни у кого, фильтр смены) воспроизводились

**`README.md`** — инструкция для жюри, учётные записи, проверка за две минуты.

### Этап 1, шаг 5 — веб-диспетчер ✅

Чистые HTML/CSS/JS без фреймворков и без сборки: жюри читает исходники
ровно в том виде, в каком их исполняет браузер.

**Экраны:** `index.html` (вход) → `select-airport.html` (аэропорт и смена,
шаг аэропорта пропускается, если он один) → `dispatch.html` (рабочий экран:
вызовы слева, карта в центре, подбор справа, состояние смены внизу).

**`js/map.js`** — SVG-карта. Рулёжки рисуются ломаными по промежуточным
точкам, поэтому аэродром узнаётся. Опрос сервера раз в 4 секунды.

Три вещи, которые пришлось решать именно здесь и которые видно только
в браузере, а не в коде:

1. **Единицы `transform`.** Трансформация применяется внутри SVG с `viewBox`,
   значит её аргументы — метры, а не пиксели. Панорамирование, собранное
   из пиксельных смещений мыши, уезжало в разы дальше движения руки, и после
   зума карта оказывалась пустой. Введены `toMapCoords` и `screenCentre`,
   вся навигация считается в координатах карты.
2. **Размер значков.** Всё содержимое лежит в масштабируемой группе, поэтому
   значок «радиусом 9» — это 9 метров: на общем плане точка в пиксель, при
   зуме — круг во весь экран. Значки вынесены в группы с обратным масштабом
   и рисуются в пикселях. Проверено: 7 px до и после трёхкратного зума.
3. **Наложение меток.** В техцентре смена стоит в одной точке, и трое
   инженеров давали на карте один кружок. `spreadOverlapping` разводит
   совпадающие метки по окружности в 11 пикселей.

Вид по умолчанию вписывается по стоянкам и техцентрам, а не по всем узлам:
рулёжка к третьей полосе уходит на километры западнее перрона и сжимала
рабочую зону в угол экрана.

**Проверено в headless-Chrome через CDP** (`Runtime.evaluate` + скриншоты):
полный путь вход → смена → карта → выбор вызова → маршрут. Отрисовано
2605 рулёжек, 179 стоянок, 3 техцентра, 6 бортов, 10 сотрудников;
маршрут построен, ETA 6.2 мин, 2 кандидата, 9 отсеянных, 1 занятый.
**Ошибок в консоли нет.**

`web-dispatcher/Dockerfile` (nginx) добавлен в `docker-compose.yml`:
`http://localhost:8080` — диспетчер, `http://localhost:8000/docs` — API.

### Этап 1, шаг 6 — развёртывание и часовые пояса ✅

**`docker compose up --build` проверен полностью.** Оба образа собираются,
сервер проходит healthcheck, база наполняется, графы грузятся в память,
веб-диспетчер раздаётся nginx. Весь браузерный сценарий прогнан
по контейнерам: вход → смена → карта → внештатный вызов на A330 →
штатный вызов на A320 с маршрутом. Ошибок в консоли нет.

**Найден и исправлен дефект часовых поясов** — виден только в контейнере,
на локальном запуске его не было. Контейнер живёт по UTC, сервер отдавал
время без пояса, браузер читал такую строку как местное время. Вызовы,
поступившие минуту назад, показывались случившимися 7 часов назад,
а «освободится до 07:11» вместо 14:11.

Для диспетчерской системы это не косметика: по времени поступления вызова
считается соблюдение регламента 15 минут.

**`server/clock.py`** — единое правило: в базе всё в UTC, наружу всё
с явным поясом (`utc_now`, `to_iso_utc`, `utc_today`). Все `datetime.now()`
заменены. Дефект оказался в двух местах независимо: в сериализации ответов
API и отдельно в представлении сотрудника для алгоритма
(`Employee.as_algorithm_dict`) — второе всплыло только на скриншоте,

### Шаг 1 — PWA инженера ✅

**`mobile-engineer/`** — установимое приложение на том же стеке
HTML/CSS/JS. Отдельный контейнер (`localhost:8081`), отдельный клиент API:
это независимо разворачиваемые приложения, и правка ради диспетчера
не должна ломать телефон инженера на перроне.

**Три экрана по сценарию §5:** вход → подтверждение выхода на смену →
рабочий. Переход между ними определяется ответом сервера, а не памятью
клиента: после перезагрузки телефона состояние не разойдётся с базой.

**Главное решение по интерфейсу.** Крупная цифра на рабочем экране —
не расчётное время в пути, а **сколько минут осталось до контрольного
срока**, с отсчётом от момента поступления вызова. Инженеру на ходу нужно
именно оставшееся время: оно уменьшается само и прямо отвечает на вопрос
«успеваю ли я», ради которого норматив и существует. При превышении
показывается «+N» красным.

**Местоположение** (`js/geo.js`): настоящий GPS через Geolocation API
и режим имитации. Имитация — не отладка, а рабочий режим: по условиям
задания реальный GPS не требуется, а снять демонстрационное видео
с перемещением по перрону Шереметьево невозможно. Координаты задаются
и вводом с клавиатуры, и касанием карты — оба способа из §10.
Отправка координат ограничена по частоте: каждая отправка это радио
и батарея, а пешком за пять секунд человек проходит семь метров.

**Карта маршрута** (`js/routemap.js`) — только ломаная до борта, цель
и своя точка. Граф Шереметьево весит около мегабайта, тянуть его
на телефон по мобильной сети ради одной линии незачем; сервер отдаёт
готовые точки маршрута вместе с вызовом.

**Эргономика §9:** цели касания от 56 пикселей (перчатки), главное
действие внизу под большим пальцем, поля 16 px (иначе iOS приближает
экран при фокусе), учёт вырезов экрана через `env(safe-area-inset-*)`.

**PWA:** манифест, иконки (PNG сгенерированы скриптом на стандартной
библиотеке), service worker кэширует оболочку. Данные не кэшируются
никогда — показать инженеру вызов из кэша опаснее, чем не показать
ничего: он может выехать к уже обслуженному борту.

**Найдено при проверке:** установка service worker шла через `cache.addAll`,
который работает по принципу «всё или ничего». Один недоступный файл
отключал офлайн-режим целиком, причём молча — ошибка гасилась пустым
`catch`. Переделано на пофайловое кэширование с переживанием отказов;
регистрация теперь проходит и активируется даже при полностью
недоступном хранилище.

**Проверено в headless-Chrome с эмуляцией телефона** (412×915, mobile):
вход → заступление на смену → «вызовов нет» → режим имитации координат →
диспетчер назначает вызов через API → вызов приходит в приложение
(ст. 31, VP-BZQ, утечка гидрожидкости, расчёт 6.2 мин, 14 мин
до контрольного срока) → принял → прибыл → завершил → снова свободен.
Service worker зарегистрирован, манифест отдаётся. Ошибок в консоли нет.

**Не проверено:** фактическое офлайн-кэширование. В headless-Chrome
CacheStorage недоступен (`caches.open` падает с внутренней ошибкой
в обоих режимах headless), поэтому проверить, что приложение реально
открывается без сети, можно только в обычном браузере или на телефоне.
Регистрация и активация service worker проверены, само кэширование — нет.

### Шаг 3 — очередь вызовов у инженера ✅

**Решение (выбрано командой из трёх вариантов):** очередь у инженера,
а не общая очередь аэропорта. Начальник смены может поставить вызов
в очередь к *занятому* инженеру с допуском — это делает рабочим список
«заняты, освободится до…» из §7: во внештатной ситуации диспетчер видит,
кто освободится первым, и сразу закрепляет за ним вызов.

**Изменение контракта §6/§8** (согласовано): статус вызова `queued`,
поля `eta_at` (абсолютное время прибытия) и `queued_at`, в ответе
`/api/me/current-call` — `queued_count`, в списке аэропортов — `centre`.

**Как устроено** — `server/services/assignment.py`, одно место для всего,
что меняет занятость сотрудника:
- инвариант: у сотрудника не больше одного *текущего* вызова (назначен,
  принят, на месте), остальные — в очереди по порядку постановки;
- время прибытия вызова в очереди считается по всей цепочке: конец
  текущих работ (прибытие + норматив 30 мин) плюс переезд **от стоянки
  предыдущего вызова**, а не от текущих координат;
- закрытие текущего вызова (с телефона или диспетчером) делает текущим
  первый вызов очереди — он сразу приходит инженеру; очередь пуста —
  инженер свободен; при подтверждении прибытия цепочка пересчитывается
  по фактическому времени.

**Исходный дефект, найденный при чтении кода.** Назначение не проверяло
занятость. Начальник смены мог назначить занятого инженера, и тогда
телефон показывал только новый вызов, а закрытие нового делало инженера
«свободным» — старый оставался назначенным без исполнителя. Вызов,
к которому никто не едет, при том что система считает его обслуживаемым.

**Дефекты того же семейства, найденные попутно и закрытые:**
- повторный «Заступить на смену» (перезапуск телефона) делал занятого
  инженера свободным — подбор предложил бы его на второй борт;
- «Уйти со смены» с незакрытым вызовом было разрешено;
- повторный подбор по уже назначенному вызову (диспетчер просто открыл
  его) переписывал поле «кого предлагала система» — ломал историю
  переопределений; кнопка «Назначить» для назначенного вызова была активна;
- API позволял начальнику смены назначить сотрудника **без допуска**
  с любой «причиной». Переопределение — выбор другого подходящего,
  а не любого (§3): теперь 422 с конкретной причиной отказа;
- в тестовых данных Гусев был «занят» без вызова — заведён настоящий
  вызов VP-BKB на стоянке 40.

**Миграция.** База в Docker лежит в томе и переживает пересборку, а
`create_all` не добавляет колонки в существующие таблицы — сервер упал бы
на старой базе. `add_missing_columns` досоздаёт недостающие nullable-колонки
при старте; для NOT NULL останавливает запуск с понятным сообщением
(такое требует Alembic). Проверено тестом на базе старой схемы.

**Интерфейс.** У диспетчера — кнопка «В очередь» у занятых (обычному
диспетчеру видна, но неактивна, с объяснением), вызов в очереди жёлтый
с абсолютным временем прибытия. У инженера — строка «ещё в очереди: N»;
после закрытия сообщение по факту ответа сервера, а не «вы свободны».

**Прочее:** устаревшая константа Starlette `HTTP_422_UNPROCESSABLE_ENTITY`
заменена (10 мест). Осталось одно предупреждение — тестовый клиент
Starlette просит заменить тестовую зависимость httpx; на сервер не влияет.

**Тестов: 92, все проходят** (+15 на очередь, +3 на «тихое освобождение»,
+2 на миграцию).

### Шаг 4 — спецтранспорт: общий парк машин ✅

**Решение (выбрано командой из трёх вариантов):** общий парк, а не
машина, закреплённая за инженером, и не одна только визуализация.
Раньше «инженер на машине» было флагом `has_vehicle` в карточке:
система не знала, где стоят свободные машины, и пеший инженер всегда
шёл пешком, даже если свободная машина стояла в сотне метров.
Требование §10 — «учёт наличия поблизости спецтранспорта и его влияния
на маршрут» — так не выполнялось.

**Модель** (`models/vehicle.py`). Машина — отдельная сущность
с позывным, статусом и местом. Флаг `has_vehicle` у инженера больше
не хранится, а выводится из машины — один источник правды вместо двух.
Место машины, которая едет с инженером, — место инженера: отдельные
координаты отставали бы от его GPS.

**Подбор** (`algorithm/transport.py`). Для инженера без машины
сравниваются «весь путь пешком» и «дойти до свободной машины
и доехать» — по каждой свободной машине. Машины не перебираются
вслепую: граф неориентированный, поэтому один проход Дейкстры
на транспорте **от стоянки** даёт время езды сразу от всех машин
(общий на весь подбор), а один пеший проход от инженера — время
ходьбы до всех машин и до борта. Полные маршруты восстанавливаются
только для выбранного варианта. При равенстве выбирается «пешком»:
занимать машину, которая может понадобиться другому, незачем.
Маршрут через машину — два участка, и оба клиента рисуют пеший
пунктиром, а на машине — сплошной линией.

**Жизненный цикл машины** (`services/assignment.py`): при назначении
резервируется (второму её не предложат) и ждёт на месте; когда
инженер подтверждает прибытие — она при нём и едет по всей его цепочке
вызовов; после последнего вызова **остаётся у борта**, где её
подберёт следующий. Незабранная машина при отмене вызова возвращается
в парк на прежнее место. Уходя со смены, инженер оставляет машину
там, где стоит.

**Демонстрация на реальном графе.** Вызов к стоянке 31: Соколов
на своей ТМ-01 — 6.2 мин; Морозов из того же техцентра без машины —
пешком 27.3 мин (нарушение регламента), но в 326 м стоит свободная
ТМ-04, и система предлагает дойти до неё — 9.5 мин.

**Найдено попутно:** ответ на назначение отдавал исполнителя (а теперь
и машину) как `None`, хотя в базе они записаны. Сессия не перечитывает
объекты после коммита, а код выставлял внешние ключи вместо связей.
Интерфейс этого не показывал — он сразу перезапрашивает список. Теперь
присваиваются связи, ответ проверяется тестом.

**Ограничение:** на базе, созданной до этого шага, в таблице
сотрудников осталась колонка `has_vehicle` (NOT NULL), а машин нет —
тестовые данные при существующих пользователях не создаются заново.
Для такой базы нужен `docker compose down -v`. Чистое развёртывание
жюри это не затрагивает.

**Тестов: 110, все проходят** (+8 на выбор способа добраться
на синтетическом графе, +11 на парк машин через API).

**Проверено в Docker на чистой базе, в браузере.** У диспетчера
на карте две свободные машины (ТМ-04, ТМ-05), в строке состояния
«свободных машин: 2»; кандидаты — «6.2 Соколов · ТМ-01»
и «9.5 Морозов · пешком → ТМ-04»; маршрут Морозова — пунктир пешком
до машины и сплошная линия на ней. После назначения ТМ-04 на карте
жёлтая (ждёт Морозова). В телефоне Морозова — «Заберите машину ТМ-04»,
метка машины и тот же маршрут двумя участками. Регрессия диспетчера
и сквозной сценарий очереди — без изменений; в карточке назначенного
вызова теперь видна машина. Ошибок консоли нет.

### Шаг 5 — второй аэропорт ✅

**Зачем.** §5 описывает шаг выбора аэропорта, но при единственном
аэропорте сервер выбирает его сам и этот экран не показывается никогда.
Пока аэропорт один, «аэропорт — контекст сессии» остаётся словами
в документации, а не проверяемым поведением.

**Домодедово (UUDD)** выгружен тем же скриптом: 1078 узлов, 1505 рёбер,
73 пронумерованные стоянки. Границы взяты из отношения аэродрома в OSM —
прежняя рамка обрезала поле с запада и юга. Техцентры привязаны
к реальным ангарам, один из них в OSM подписан как Repair Base.

**Аэропорт с другой геометрией — отдельный контрольный случай.**
В Домодедово пешком в регламент попадают 2 стоянки из 73 (в Шереметьеве —
35 из 179), на машине — все 73. Спецтранспорт там не удобство,
а условие выполнения регламента.

**Доступ по аэропортам.** Диспетчер Смирнова привязана к обоим —
у неё появляется шаг выбора. Начальник смены Белов привязан только
к Шереметьево: на нём проверяется запрет чужого аэропорта. Инженер
Беляев — учётная запись Домодедово.

**Проверено.** Тестов 118 (+7 на второй аэропорт, +1 на автоподстановку
единственного аэропорта): списки сотрудников, бортов, машин и вызовов
не смешиваются; чужой вызов по идентификатору недоступен (404); граф
второго аэропорта отдаётся; подбор в Домодедово идёт через машины.
В браузере: экран выбора показывает обе карточки, в Домодедово
отрисованы 1505 рулёжек, 73 стоянки, 2 техцентра, 4 борта, и кандидаты —
«8.5 Беляев · ДМ-01», «11 Гончаров · пешком → ДМ-02», «23 Жуков».
Ошибок консоли нет.

### Шаг 6 — формальные тесты сценариев ✅

**Зачем.** §10 требует не менее пяти контрольных сценариев, сравнения
с «интуитивным» выбором диспетчера и обоснования оптимизации. Юнит-тесты
это проверяют, но показать жюри «зелёный прогон» нельзя: в нём не видно,
кого система выбрала и почему отказала остальным.

**Отчёт вместо документа.** `server/scenarios.py` наполняет временную базу
тем же `seed.py`, что и стенд, прогоняет 9 сценариев на настоящих графах
и пишет `docs/scenarios.md`. Таблицу никто не правит руками — она
пересобирается командой, поэтому разойтись с кодом не может.

**Как моделируется интуитивный выбор.** Ближайший по прямой свободный
сотрудник смены: без проверки типа ВС и срока действия отметки и без
знания, где стоят свободные машины парка. Время в пути ему считается
честно, по графу, — иначе сравнение было бы подтасовкой.

**Результат.** В 7 сценариях из 9 ближайший по прямой юридически
недопустим: у стоянки 31 Волков стоит у самого борта, Орлов в 94 метрах,
и оба отсеиваются — у первого допуск на B777, у второго истекла отметка.
Главный выигрыш системы — не минуты, а недопущенные назначения, которые
по бумажным данным выясняются уже у борта. Максимальное время расчёта —
29 мс при ограничении 10 000 мс.

**Проверено.** Тестов 129 (+11): каждое утверждение отчёта закреплено
отдельным тестом, включая маршрут через машину парка (Морозов идёт
до ТМ-04 и укладывается в регламент) и обязательное наличие причины
отказа, когда кандидатов нет.

### Шаг 7 — снятие исполнителя и переназначение ✅

**Зачем.** Назначение не окончательно: инженер застревает на прошлом
борте, машина не заводится, вылет переносят. Закрыть такой вызов нельзя —
работа не сделана.

`POST /api/calls/{id}/unassign` с обязательной причиной возвращает вызов
к подбору. Сотрудник освобождается или берётся за следующий вызов очереди,
машина возвращается в парк — по фактическим координатам инженера, а не
у борта, куда он не доехал. Расчёт прошлого назначения и прежнее
предложение системы стираются: иначе назначение любого другого выглядело
бы как переопределение и требовало бы роли начальника смены. Снятый
не предлагается повторно, но виден в отказах с причиной. В приложении
инженера вызов не исчезает молча — приходит сообщение.

### Шаг 8 — конструктор: аэропорты, люди, машины, борта ✅

**Зачем.** Аэропортов было два, данные — только из seed. Экран
`admin.html` позволяет завести всё это через интерфейс.

**Аэропорт по коду ИКАО.** Границы поля находятся в OSM по самому коду,
граф строится тем же кодом, что и офлайн-выгрузка (разбор OSM вынесен
в `server/services/osm_import.py`; пересборка UUEE из сохранённого ответа
совпала с закоммиченным файлом до байта). Публичный Overpass нестабилен,
поэтому запрос перебирает зеркала. Это единственное обращение сервера
в сеть — по команде администратора.

**Разметка по точкам** поверх спутникового снимка: стоянка, техцентр,
перекрёсток, связь, удаление. Новая стоянка сама присоединяется
к ближайшей точке сети; клик по серой точке превращает её в стоянку —
так доводится импортированный аэропорт, в котором OSM не знает стоянок
(у Пулково их нет ни одной). Длины считает сервер; у рёбер, пришедших
из OSM, сохраняются настоящие длины и изгибы, а опорная точка не меняется.
Граф без стоянки, без техцентра или с несвязанными точками не сохраняется.

**Хранение.** Созданные аэропорты лежат в базе (том), а не в каталоге
графов (образ) — иначе исчезли бы при пересоздании контейнера. Реестр
графов объединяет оба источника; на старте графы из базы поднимаются
в память. Миграция научилась добавлять NOT NULL колонки с умолчанием.

**Проверено.** Тестов 179. Сквозной тест проходит весь путь: пустая карта →
разметка → инженер с логином → борт → вызов → подбор по нарисованным
рулёжкам (техцентр → перекрёсток → стоянка) → вызов в телефоне инженера.
В браузере тот же путь пройден через интерфейс; настоящий импорт Пулково
(868 точек, 1308 рулёжек за 11 с) доведён в редакторе до рабочего
состояния, и подбор в нём идёт по сети: 694 м против 519 м по прямой.
Скриншоты выявили и исправлены: схлопнутую до 92 px карту редактора
(display: flex перебивал атрибут hidden у вкладок), дублированную
отрисовку точек, незаметный на снимке перекрёсток, ложную подпись
«Граф: OpenStreetMap» под нарисованным вручную аэропортом.
